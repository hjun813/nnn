# 테스트 및 운영 계획

## 1. 테스트 전략

### 단위 테스트

- D-Day와 주간 범위 계산
- 시간대 및 서머타임 경계
- 목표일 검증
- 진행률 계산
- 다음 행동과 우선순위
- 상태 전환
- URL 정규화 및 사설 주소 판정

### 통합 테스트

- 인증 사용자별 데이터 격리
- 공고·작업 transaction
- Applied/Expired/Archived 이력
- 알림 중복 방지
- 분석 confirm 멱등성
- DB migration

### E2E 테스트

1. 가입 → 직접 등록 → 작업 완료 → 지원 완료
2. URL 분석 성공 → 수정 → 저장
3. URL 분석 실패 → 직접 입력 → 저장
4. 목표일이 실제 마감 이후인 입력 차단
5. 마감 공고 Expired 처리 및 보관
6. 다른 사용자 리소스 접근 거부

### AI 평가

- 골든셋을 CI의 비결정적 모델 호출과 분리한다.
- 파서와 validator는 항상 CI에서 테스트한다.
- 모델 평가는 예약 실행하고 품질 회귀를 배포 조건으로 사용한다.

## 2. 필수 경계 사례

- 자정, 윤년, 월·연도 경계
- 날짜만 있고 시간이 없는 공고
- 상시 채용, 마감 미정, 이미 마감
- 동일 URL의 tracking query 차이
- 제출물이 없거나 모두 Not Required
- Applied 후 상태 되돌리기
- 분석 요청 중 새로고침·중복 요청
- 리디렉션이 내부 주소로 향하는 URL
- 매우 큰 페이지, 빈 페이지, 비HTML 응답

## 3. 운영 지표

- API 오류율과 p95 latency
- 분석 성공률·처리 시간·실패 코드 분포
- cron 마지막 성공 시각
- 생성돼야 했지만 누락된 알림 수
- DB 연결·저장 공간·느린 query
- 로그인 실패 급증과 rate-limit 발생량

## 4. 알림 기준 예시

- 5분간 API 5xx 비율 5% 초과
- 분석 실패율 30분간 기준선의 2배 초과
- cron이 예정 시각 이후 30분 내 완료되지 않음
- DB 연결 실패 또는 저장 공간 임계치 도달

실제 임계치는 베타 트래픽 기준으로 조정한다.

## 5. 개인정보와 보안

- 최소 데이터만 수집한다.
- 비밀번호를 직접 관리하는 경우 검증된 해시를 사용한다.
- 전송·저장 구간 보호와 secret 분리를 적용한다.
- 외부 HTML, 사용자 메모, AI 결과를 신뢰하지 않는다.
- 로그와 analytics에 자기소개서 원문을 넣지 않는다.
- 계정 삭제, 데이터 내보내기, 보존 기간을 정책화한다.
- 의존성 및 취약점 점검을 정기 실행한다.

## 6. 백업과 장애 복구

- 운영 DB 자동 백업과 보존 기간 설정
- 정기적인 복원 연습
- migration 전 백업 또는 point-in-time recovery 확보
- AI 공급자 장애 시 직접 등록 유지
- scheduler 장애 후 누락 구간을 재처리할 수 있는 멱등 작업

## 7. 출시 체크리스트

- P0 인수 조건과 E2E 통과
- 권한·SSRF·XSS·CSRF 점검
- 개인정보처리방침과 이용약관 준비
- 운영 환경 secret 및 도메인 설정
- 백업과 오류 알림 확인
- analytics 이벤트 검증
- 장애 시 AI 기능을 끌 feature flag
- 고객 문의 및 데이터 삭제 경로 준비
